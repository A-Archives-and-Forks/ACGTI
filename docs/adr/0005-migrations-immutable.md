# 0005. 已发布的 D1 迁移文件不可回改

- 状态：已接受（2026-05，来自真实事故）

## 背景

迁移系统按「文件是否执行过」记录状态。项目早期曾把已发布的 `0001_init.sql` 回改为想要的最终形态（补列），随后又新增了含相同列的 `0006_add_feedback_answers.sql`。结果：

- 已执行过旧版 0001 的线上库不会重跑 0001，新增列靠 0006 补齐——线上正常；
- **全新环境**（新预览库、CI 干跑、协作者本地）按序执行时会先在 0001 建出「超前」的表结构，0006 再次加列直接报 `duplicate column` 而失败。

同一份迁移序列在两类环境产生分叉，这是迁移系统的经典反模式。

## 候选方案

1. **继续回改旧迁移**：线上库与新库永远对不齐，不可行。
2. **恢复 0001 最初形态 + 新增修补迁移**：0001 回到只建最初的表；后续结构变化全部走增量迁移；已受「回改窗口期」影响的存量库（预览库）手动执行一次性修复 SQL。
3. **迁移前加 IF NOT EXISTS 防御**：治标，掩盖分叉事实。

## 决定

采用方案 2，并立此规矩：**迁移文件一旦在任何环境执行过就视为不可变**，改结构只能新增迁移。同时在 CI 增加防护：每次构建都在全新本地库上按序干跑全部迁移（`wrangler d1 migrations apply --local`），分叉会在 CI 第一时间暴露。

## 后果

- 正面：全新环境与线上环境的迁移序列重新收敛；CI 干跑让此类问题永不再静默发生。
- 负面：0001 与「项目当前表结构」不再一一对应，读迁移文件理解结构需要按序拼接（这在迁移系统中本就是常态）。
- 教训泛化：任何按状态增量演进的产物（迁移、事件 schema、广播消息版本）都应视为 append-only。
