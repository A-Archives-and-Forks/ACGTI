# 0003. 测评内核数据驱动：题库 / 权重 / 角色全部为受校验的 JSON

- 状态：已接受（2026-04）

## 背景

产品的核心竞争力是「题目设计 + 角色映射 + 结果文案」的内容迭代速度：改一道题的权重、加一个角色都不应该需要改引擎代码。同时内容数据量大（39 题、8 原型、113 角色 × 4 语言），人工维护极易出现引用漂移（角色签名指向不存在的题目、图片路径与角色文件脱钩、多语言条目缺失）。

## 候选方案

1. **内容硬编码在引擎旁的 TS 模块**：类型安全最好，但内容修改=代码修改，贡献者门槛高。
2. **数据库/Headless CMS**：运行时灵活，但引入部署依赖与鉴权，本地开发体验差。
3. **源数据 JSON + 构建期聚合 + 校验门禁**：`src/content/characters/*.json` 为唯一人工编辑层；`scripts/build-character-data.mjs` 聚合生成 `src/data/*.json` 与后端 `functions/api/_data/characterBrief.json`；`scripts/validate-character-data.mjs` 在构建与 CI 中执行结构、引用、图片、多语言一致性等十余类校验。

## 决定

采用方案 3，并把它升级为**门禁**：`npm run build` 第一步就是数据校验，任何漂移直接构建失败。引擎（`src/utils/quizEngine.ts`）只从数据读取维度与权重，唯一的例外是逐题权重覆盖表 `questionDimensionWeights.json`——它由真实反馈数据校准产出（见 `analysis/` 流水线），语义为「整体替换」并在引擎内有显式注释。

计分结果的角色排序由四路信号加权合成（MBTI 匹配 0.25 / 原型累计 0.28 / 六维向量余弦 0.27 / 角色签名 0.2），权重常量集中在引擎顶部，配合单元测试（`tests/quizEngine.test.ts`）保证量纲与确定性。

## 后果

- 正面：加角色 = 加一个 JSON 文件再跑构建；内容 PR 可由非程序员完成；数据漂移在 CI 拦截而非线上曝光。
- 负面：校验脚本本身需要持续维护（新增内容字段时要同步补规则）；JSON 无类型提示，靠校验脚本弥补。
- 演进方向：多测评框架（Big Five / 九型）若要支持，应先抽象「框架描述 JSON」（维度定义 + 计分函数注册），而不是在现有引擎上硬编码新维度。
