# 0007. i18n 角色文案单一数据源，按需加载

- 状态：已接受（2026-08，来自真实事故）

## 背景

角色文案需要四语言（简中/繁中/英/日），体积约 232KB（113 角色 × title/note/tags）。历史上曾把角色译文同时维护在两处：`src/i18n/messages.ts` 内嵌一份、`characterMessages.json` 一份，两份数据随内容迭代逐渐漂移，出现过「页面语言已切换、角色解析仍是旧译文」的静默不一致。

同时首屏 i18n 主包被这 232KB 拖累（gzip 后约 100KB），对打开速度伤害明显，而角色文案只在结果页/图鉴页才需要。

## 候选方案

1. **全部并入 messages.ts**：单源但首屏包巨大。
2. **按语言拆分多个静态 bundle，全量预载**：首屏仍载入当前语言全部角色文案。
3. **构建产物单一数据源 + 动态 import 按需加载**：`characterMessages.json`（由角色源文件构建生成）是唯一事实源；进入需要角色文案的页面时动态 import；`t()` 在文案未就绪期间回退源数据中文，避免闪空。

## 决定

采用方案 3。`src/i18n/characterMessages.ts` 维护模块级缓存与加载 Promise，`ensureCharacterMessages()` 幂等加载；`messages.ts` 中删除全部内嵌角色条目，数量类文案（题目数、角色数）用手工常量并由校验脚本与真实数据比对，防止删源后失同步。

## 后果

- 正面：首屏 i18n 块从 421KB 降至约 147KB（gzip 183KB→58KB）；角色文案只改角色源文件一处，漂移类 bug 结构性消除；加载失败回退中文而不是白屏。
- 负面：动态加载存在一次性等待（本地缓存后无感）；`t()` 需要维护回退语义，贡献者新增角色文案时要理解「源文件 i18n 字段 + 构建聚合」的链路（由校验脚本兜底）。
